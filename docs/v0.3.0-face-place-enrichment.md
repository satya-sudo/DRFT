# v0.3.0 Face and Place Enrichment

This document is the working reference for the automatic face and place detection effort planned for `v0.3.0`.

It is intentionally implementation-oriented so we can come back to it during backend, mobile, and later web work.

## Goal

Add a private, self-hosted enrichment pipeline that:

- detects faces in uploaded images
- extracts and normalizes place data from EXIF GPS
- groups likely same-person faces into suggested people clusters
- keeps all results private to the library owner
- requires user confirmation before turning suggestions into stable people/place organization objects

## Principles

- keep DRFT single-node for `v0.3.0`
- keep uploads fast by processing enrichment asynchronously
- scope inferred entities by library owner `user_id`
- do not assume a detected person is a DRFT account
- prefer conservative suggestions over aggressive auto-merging
- keep image enrichment local on the DRFT host

## Delivery Steps

### Step 1: Backend foundation

- add DB tables for enrichment jobs, per-file enrichment status, face detections, person clusters, places, and place suggestions
- add backend config flags for enabling enrichment and controlling worker behavior
- enqueue enrichment work for newly uploaded images
- add per-user enrichment status and backfill APIs
- keep this stage safe even before analyzers are fully implemented

Definition of done:

- migrations apply cleanly
- image uploads can enqueue enrichment jobs
- users can see enrichment queue status
- users can trigger backfill for existing images

### Step 2: Worker loop and job lifecycle

- add a dedicated enrichment worker process or worker mode
- claim jobs from PostgreSQL using row locking
- add retry, stale-job recovery, and structured logging
- mark files and jobs through `pending`, `processing`, `completed`, and `failed`
- use a placeholder processor first so the queue lifecycle is proven before model integration

Definition of done:

- worker can claim and complete placeholder jobs safely
- restart does not corrupt queue state
- duplicate active jobs are prevented

### Step 3: Place extraction

- extend metadata extraction to read EXIF GPS when present
- create normalized place suggestion records from GPS
- store locality-level place information first
- keep source and confidence fields for later review UX

Definition of done:

- GPS-tagged images produce place suggestions
- images without GPS skip place creation cleanly
- place suggestions are scoped per library owner

### Step 4: Face detection

- run face detection only for images
- store bounding boxes and confidence scores
- prepare stable interfaces for later embedding/clustering work
- keep low-confidence detections out of review by default

Definition of done:

- images with faces produce detection rows
- empty or non-face images do not create noisy results
- detections are tied to files and user ownership

### Step 5: Person clustering

- add face embeddings or equivalent similarity data
- cluster detections within a single `user_id`
- create suggested person clusters without auto-naming
- support conservative regrouping and future reclustering

Definition of done:

- likely same-person detections appear in the same suggested cluster
- bad cross-person merges are minimized
- clustering never crosses library ownership boundaries

### Step 6: Review APIs

- add people list/detail endpoints
- add place list/detail endpoints
- add confirm and reject flows for both
- add member-removal or split support for bad person clusters

Definition of done:

- mobile can fetch suggested people and places
- a user can confirm or reject suggestions
- confirmed entities become stable organization records

### Step 7: Mobile first UX

- add `People`, `Places`, and `Review` surfaces in mobile
- show suggested clusters and suggested places
- support confirm, reject, and basic cleanup actions
- show enrichment progress during backfill and ongoing uploads

Definition of done:

- user can upload, wait, review, and confirm suggestions from mobile
- confirmed people and places feel like first-class organization views

### Step 8: Hardening and rollout

- add backfill safeguards for large libraries
- improve metrics and logs
- document system requirements and deployment knobs
- add migration notes for existing DRFT installs

Definition of done:

- a `10k-50k` image library can be backfilled on recommended hardware
- errors are observable and recoverable
- Docker deployment docs are updated

## Current Decisions

- release target: `v0.3.0`
- rollout order: backend first, mobile first for UX, web later
- runtime model: fully local
- hardware baseline: CPU-only Linux box
- first media scope: images only
- people flow: detect and cluster, then user confirms
- places flow: EXIF GPS plus normalization into human-readable place suggestions
- review policy: suggested until confirmed

## Open Follow-ups

- choose the concrete local face detection and embedding runtime
- choose the local place normalization dataset and import format
- decide whether the worker runs as a separate binary or as a second mode of `drft`
- decide when confirmed people/places should integrate with generic tags
